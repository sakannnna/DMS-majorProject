# 项目工作与记录规范

本文供用户与Agent协作时查阅：先确认会改变业务范围的决定，按功能实现和验证，再同步维护相关说明。规范已采用；第二阶段按已确认设计分步实施；本批只完成独立题目、版本与问卷选入，完成后停止，未经用户明确要求不自动记录AI日志；报告正文由用户撰写。

依据：根目录《大作业一第一阶段.docx》及《大作业一：需求变更.docx》。第一阶段重点为第二节项目说明、第三至七节技术与交付要求及末尾初始用户需求；第二阶段按八项需求变更扩展。下文的目录、编号和记录格式是用户已采用的项目约定，不是教师规定的文件格式。

## 作业约束

- 开发基于 MongoDB 的简化在线问卷系统。所有业务数据存入 MongoDB，不使用关系数据库或现成问卷系统框架；语言和框架不限，界面可以简单。
- 文档须解释 MongoDB 设计理由，包含系统说明、数据库设计、API 说明及关键逻辑说明。最终报告须涵盖目标、系统设计、MongoDB 设计、跳转、校验、AI 使用、测试结果及问题解决。
- 必须编写测试用例并写清步骤，至少覆盖创建问卷、添加题目、跳转逻辑、校验、提交问卷、统计。允许自动、手工或 API 测试。
- AI 日志必须真实记录工具、提示词、产出和修改情况；最终报告说明 AI 的帮助、实际错误、用户的修改和设计。
- 第二阶段必须在第一阶段系统上扩展，保留核心结构、旧数据和主要功能，记录设计、数据结构、程序及兼容性变化。

## 工作流程与确认边界

1. **维护工作规范**：依实际工作原位调整流程、文档位置和记录格式，不将规范确认另设为阻塞步骤。
2. **需求与设计分析**：整理需求、权限、流程、技术栈建议、数据主体与 MongoDB 集合草案；每项注明“文档明确要求”“AI 建议”或“待确认”。附原文节名，避免将建议写成作业要求。
3. **集中确认总体方案**：将技术栈、范围、数据方案及关键未定问题一次提交用户。问题写明影响、推荐选项以及是否阻塞开发。用户决定需求取舍和总体设计；常规字段、接口命名及实现细节由 Agent 在已确认范围内决定并记录必要理由。未确认前不写系统代码。
4. **按功能分步开发**：建议顺序为账号与权限 → 问卷和题目 → 校验与跳转 → 填写提交 → 统计。可因依赖调整，不扩张已确认范围。每批完成一个可验证的功能，补充相关文档；仅在用户明确要求时追加AI日志；发现会改变已确认范围或总体设计的问题时，集中说明后再实施相关变更。
5. **验证与交付**：执行六类必测用例及相关权限、异常和回归检查；逐项核对需求、实际结果与提交材料，报告未完成项和已知问题，不以“已有代码”代替验收。

每个功能使用同一小闭环：明确验收条件 → 实现 → 执行验证 → 记录实际结果及必要修正。对无关功能不重复测试，对修改影响的功能补做回归。

第一阶段交付时保存可复现基线：代码版本、依赖与启动方式、MongoDB 结构说明、测试结果及演示数据准备方式。建议使用 Git，阶段交付打标签；尚未启用 Git 时明确记录实际版本和备份位置，不声称已有提交。第二阶段沿用该基线，记录结构变化、旧数据处理和旧功能回归，不预先实现尚未发布的第二阶段功能。

## 项目文档目录

以包含README和start.bat的“数据库大作业（分段）”目录为项目根目录。保留原始需求文件不修改。以 UTF-8 Markdown 为工作文档，减少重复维护；教师另有格式要求时再导出。

```text
数据库大作业（分段）/
├─ 大作业一第一阶段.docx       第一阶段原始要求
├─ 大作业一：需求变更.docx     第二阶段原始要求
├─ README.md                  项目入口、环境配置、启动及测试命令
├─ docs/
│  ├─ 工作与记录规范.md        协作流程和记录维护规则
│  ├─ 需求与设计.md            需求清单、权限流程、技术与数据设计、关键逻辑
│  ├─ API说明.md               与实现一致的接口说明；可链接自动生成的接口文档
│  ├─ 测试记录.md              用例定义、执行批次、实际结果、遗留问题
│  ├─ AI使用日志.md            保留第一阶段；用户明确要求时按实际批次追加
│  ├─ 阶段一报告.md            汇总已有材料并逐项核对交付
│  └─ evidence/               必要的测试输出、截图和阶段基线说明
└─ tests/                     可执行自动测试；文档保留人可读的输入和预期
```

文件按实际需要建立，不创建空壳。已有代码模块的入口在README维护，本文不重复列代码清单。

- 需求使用简短编号 R01、R02 等；测试使用 T01、T02 等。用编号或链接串联需求、测试和交付核对，不另建重复台账。
- “需求与设计”维护当前有效方案和确认状态；当前有效决定直接更新此文；用户明确要求记录时，历史过程进入AI日志，不另建决策台账。用户确认后记录日期、确认范围和准确摘要。
- 报告引用设计、日志和测试证据，补充必要总结；不再手工维护另一套不同版本的需求和结果。
- 截图、命令输出只保存能证明结果或帮助复现的问题证据；常规成功无需逐步截图。不记录明文密码、连接凭据或私人数据。

## 文档增长与维护

默认原位更新。禁止按每轮工作新增总结、补充说明或检查报告。当前需求、设计和 API 各只有一份有效说明，历史方案不与当前方案并列充当操作依据。

| 文件 | 主要读者和唯一职责 | 内容边界 |
| --- | --- | --- |
| README.md | 用户、教师和接手 Agent；找到材料并运行项目 | 保存入口、当前状态、环境及启动测试方法，链接详细说明，不复制设计 |
| 工作与记录规范.md | 用户和 Agent；按约定协作和记录 | 只保存当前流程与模板，不记录工作经过 |
| 需求与设计.md | 用户作总体决策、开发者实现和教师审阅设计 | 唯一的当前需求、权限、流程、技术与数据设计及未定问题；保留明确的确认状态 |
| API说明.md | 接口使用者与测试者；调用实际接口 | 模型维护精确契约并生成OpenAPI；本文解释主要输入输出和完整调用示例，不另存schema副本或复制数据库字段表 |
| 测试记录.md | 验证者与教师；复现并判断结果 | 用例定义及实际执行记录，不复制设计说明；执行历史可保留以追溯修复 |
| AI使用日志.md | 用户与教师；核对 AI 和人的实际贡献 | 提示词、历史决定与变更原因、产出定位、验证事实；引用产物和证据，不复制全文 |
| 阶段一报告.md | 教师；评估阶段成果和交付完整性 | 根据作业栏目归纳完成情况与证据，引用当前说明；提交导出物标明对应基线，不作为另一份持续维护的需求或设计 |
| evidence/ | 验证者；核查原始结果或阶段基线 | 仅保留必要输出、截图等证据，不存每轮叙述性报告 |

新建文件前先判断能否更新既有文件。确需新建时，必须有独立读者和使用场景、明确唯一职责、与已有内容不重复，并在 README 入口提供链接；证据目录可通过测试记录或日志索引后由入口链接到该索引。

每份主要说明须让不熟悉代码的读者独立理解用途、关键操作和限制；先解释场景，再引入必要术语。允许为理解而简短概括其他文档的结论，但完整规则、字段表与执行结果仍只有一个责任位置，不能只给链接而省略解释。

每批变更同步更新受影响的当前说明。第二阶段未经用户明确要求，不自动新增AI日志；下文日志模板仅在用户明确要求记录时适用，第一阶段既有日志保留。需求变化更新需求与设计，接口变化更新 API 契约，测试变化更新用例与结果；同一事实只在其责任文件维护，其他位置用链接引用。

每批相关代码变更的收尾必须同时完成：

1. 输入、输出、权限或错误结构变化：更新模型及API说明对应段落，并检查app.js的消费位置；响应契约测试T19随接口回归执行。
2. 数据或业务语义变化：原位更新需求与设计中对应规则及扩展影响，清除被替换的说明；测试步骤和真实结果只进测试记录。
3. 运行或依赖变化：更新README中的配置与检查方法，不写“进程当前仍在运行”“本机已安装”作为长期事实。
4. 检查本批文档链接、确认与实现一致、没有复制其他责任文件的说明；执行 `python scripts/check-docs.py` 或传入相关文件路径。检查脚本只验证链接和围栏，语义仍须人工或Agent对照代码检查。用户要求记录时再把历史和原因写入AI日志，报告只引用证据。

相关说明没有同步完成时，不把这批代码标为收尾完成；不等到里程碑才集中清理。里程碑检查只补查跨文档入口与遗漏。

每个里程碑检查 README 入口、重复内容、过时状态及链接：合并重复、删除无用内容、修正失效链接，并核对当前说明与实际产物一致。检查结论在当次回复说明；仅在用户明确要求时写入AI日志，不另建检查报告。

归档只保留能说明重要决策、阶段交付或兼容性变化的材料，注明阶段或版本并从入口链接。已记录的普通过程留在AI日志，未经要求不为此补记；错误或无用副本直接清理；归档不能代替清理。第二阶段的有效说明继续原位更新，第一阶段快照通过 Git 基线或必要的交付包追溯。

## 测试记录格式

用例定义与执行记录分开：同一个用例可以多次执行，失败结果保留，修复后追加复测结果。

用例定义采用以下简短条目；无须填写无关字段。

```text
T编号  用例名称
关联需求：R编号
方式：网页操作 / API请求（注明实际网络或进程内客户端） / 直接函数调用；另注明执行主体
前置条件：账号角色、问卷状态、所需数据
步骤与输入：可复现的操作或命令，明确具体输入
预期输出：响应、界面提示，以及必要的 MongoDB 数据变化或统计值
```

每个执行批次写一次日期、代码版本、环境、数据准备方式和执行人，随后使用表格：

| 用例 | 实际输出与证据 | 结果 | 问题与后续处理 |
| --- | --- | --- | --- |
| T编号 | 实际观察或输出文件链接 | 通过 / 失败 / 未执行 / 阻塞 | 原因、修复位置及复测关联；无则写无 |

表中为格式占位，不代表已有用例执行。

- 至少覆盖作业六类测试。设计确认后，为每类补正常情形和有意义的异常或边界；跳转需覆盖相关分支，统计使用预先算出的固定数据核对。
- 根据已确认权限和规则补充越权访问、登录限制、截止与关闭、重复填写、匿名身份处理及多人提交等检查，不在本轮替这些规则作决定。
- 只有实际执行并符合预期才能写“通过”。未运行写“未执行”；无法运行写“阻塞”及原因。代码审阅、文档核对和系统运行测试分开表述。
- 自动测试保留命令及结果摘要；手工测试保留操作、输入和实际输出。失败需记录实际现象、修复原因及复测结果，不为报告刻意制造错误。

## AI 使用日志格式

按“可说明清楚的一批工作”追加，而非每次工具调用一条。需求分析、设计、编码、排错和验证均属于可记录的AI工作；此模板仅在用户明确要求记录时启用，不自动记录第二阶段工作。提示词可以用准确摘要，影响结果的条件或否定约束必须保留；关键原话可直接引用。

```text
日期与工作批次：
工具与执行主体：如 Codex；AI / 用户分别做了什么
用户提示词或准确摘要：
AI 产出：方案、文件路径、代码位置或版本；没有代码就明确写无代码
实际验证：谁执行、具体方法、观察结果和证据；未执行说明原因
修改及原因：相对已有方案或代码改了什么、由谁修改、为什么；无则写无
用户决定：用户已明确决定的内容；AI 建议待确认时不得写成已采纳
未完成或待确认：有则列出，无则写无
```

- AI 自动编辑、执行命令和修复属于 AI 完成的工作；用户提出约束、选择方案、自己改写代码或亲自测试分别注明。不能将 AI 修改记为“本人修改”。
- 建议、已生成、已检查、已运行、已通过和用户已确认具有不同含义，按事实使用。
- 不要求逐字粘贴整段代码或完整对话；记录足以定位和复核的路径、版本、关键摘要与必要证据。
- 用户明确要求记录AI日志时，按实际批次更新；补记须标明补记，不编造测试、错误或用户决定。纠正错误记录时保留简短更正说明。
- 最终 AI 使用说明从真实日志归纳。若没有观察到 AI 错误或用户手工改代码，就如实说明，不为了凑栏目虚构经历。
